# Decisions log

Append-only. One entry per decision or surprise, newest at the bottom. Each entry: context, what we did, what we rejected, what it cost, what we'd say if asked.

## 2026-10-07 — Graviton nodes instead of x86
Laptop is arm64 (Docker 28, aarch64). Cross-building for amd64 adds minutes per image and a class of "works locally, fails in pod" bugs. Chose `m7g.large` managed node group so images build natively. Cost: ARM wheels for a few dev deps could be missing; Flask's dev extras are pure Python, so low risk.

## 2026-10-07 — EC2 on-demand vCPU quota is 5
`L-1216C47A` = 5 vCPU in us-east-1 on a fresh-ish account. Three `m7g.large` is 6. Requested increase to 32 (`9c866f461a7d420e8c3cc67bea590b15sI75Z0QF`, PENDING). Approved within hours to **64** (more than asked). Spot quota is also 5, so spot would not have helped at the time. Lesson for the talk: capacity is a quota problem before it is a scheduler problem.

## 2026-10-07 — Root credentials in the `personal` profile
`aws sts get-caller-identity` returns the account root. Works, but should be an IAM user with admin + MFA. Flagged, not blocking.

## 2026-10-07 — Flask's test suite takes 1.1 seconds, not 30
494 tests, 1.14s locally; `uv sync` of test deps ~1.5s warm, ruff 0.3s. The "expensive" part of a task is not the tests. It is image pull + clone + dependency install, i.e. everything the warm pool pre-pays. Good for the thesis, bad for a dramatic demo: pytest will not be the visible wait. Expect the LLM call to dominate the warm path.

## 2026-10-07 — Read-only root filesystem vs a baked-in clone
The clone is baked into the image at `/opt/seed/flask`. With `readOnlyRootFilesystem: true` the runner cannot write there, so on boot it `copytree`s the seed into the `/work` emptyDir and does all git/uv work there. Cost: one copy per pod (~hundreds of ms, measured in `warm_seconds`). Alternative was dropping the read-only root, rejected: it is the cheapest hardening we have.

## 2026-10-07 — API Gateway → SQS direct integration cannot forward the HMAC header
Plan was GitHub → API Gateway HTTP API → SQS with the `X-Hub-Signature-256` header copied into a message attribute, verified later by the controller. The SQS-SendMessage integration only accepts a *single* mapping expression or a static string per request parameter; a header reference embedded inside the MessageAttributes JSON fails with `Unable to resolve property MessageAttributes from source ...` (HTTP 400). Lowercasing the header names did not help; it is a structural limit. Fix: a 60-line Python Lambda (arm64, 128MB) in front of the queue that verifies the HMAC, drops pings/unwanted actions, and forwards accepted events with attributes. Net effect is better than the original plan: nothing unauthenticated ever reaches the queue, and the controller no longer needs the webhook secret. Cost: one more AWS resource and ~1 hour. Second gotcha: Terraform could not swap the route's integration in place (409 on delete while the route still referenced it); `state rm` + manual delete.

## 2026-10-07 — The KEDA baseline pod has to hold AWS credentials
With KEDA ScaledJob there is no dispatcher: each Job pod must `ReceiveMessage` itself, so the untrusted pod gets an IAM role (Pod Identity) and a mounted service-account token. That is exactly the trust leak the controller design removes. Keeping the baseline anyway for the cold-start comparison, with the message pull isolated in an init container so the runner image itself stays free of the AWS SDK.

## 2026-10-07 — "Exit after one task" does not work inside a Deployment
Original plan: runner process exits after a task, pod dies, ReplicaSet refills. Reality: a Deployment pod has `restartPolicy: Always`, so the *container* restarts in place with the same pod name and the same dirty `/work` emptyDir. The pod is not ephemeral at all. Fix: the runner stays up but flips its readiness to 503 (`state=done`), and the controller deletes the pod when the result arrives. Pod deletion is the real ephemeral boundary; the ReplicaSet still refills. Side benefit: a crashed controller leaves "done" pods unready instead of re-assignable.

## 2026-10-07 — First warm-vs-cold numbers (n=1 each, same 4-line PR)
Cold (KEDA ScaledJob, no pool): push → pod scheduled 15s → pod total 16s → ~35s to result.
Warm (controller + pool of 4): push → queued → assigned in 0.7s → result in 4.5s. pytest itself 3.4s on m7g.large (1.1s on the laptop).
Everything the warm pod pre-pays (image pull, seed copy, dep install) is what the cold path spends. Proper distributions come from the eval run.

## 2026-10-07 — Historical bug corpus yields ~8 real bugs, not 30
Scanning 5.5k upstream Flask commits for fix-like messages gives 68 candidates since 2016, but only the ones whose *source* hunks reverse-apply cleanly onto today's main are usable, and several survivors are not bugs ("fix mypy finding", docstring quotes). Net: 4 red + ~4 real green historical bugs (IPv6 server-name parsing, IPv6 session cookies, provide_automatic_options override, secret-key rotation ordering, CLI `--help` handling). Flask is small, old, and well-tested; most fixes are entangled with refactors. Supplement: single-operator AST mutations of `src/flask` that leave the suite green, labeled `synthetic: true` and reported separately. Honest framing for the slide: historical = "bugs maintainers actually shipped", synthetic = "defects nothing tests". Clean set: 20 recent upstream changes replayed forward (base = main minus the commit, head = main), so the reviewer sees a real merged diff with green tests.

## 2026-10-07 — First real catch, and a corpus leak
First reviewed PR (reverted IPv6 server-name fix, suite green): gpt-6-astra posted `REQUEST_CHANGES` with one inline finding at `src/flask/app.py:721`: "`[::1]:8080` parses as host `[` and port `:1]:8080`". Correct, specific, 10s LLM time, 19k input tokens, no tool calls. End to end 15.7s.
But the summary also said "the existing test covering this behavior was removed", because the green variant's diff included the test deletion. That is a giveaway a real sloppy PR would not contain. Fix: for historical green variants the test removal now lives in a `bug-base/<sha>` branch and the PR diff is source-only. Synthetic mutants never had this problem. Also: GitHub refuses APPROVE/REQUEST_CHANGES from the PR author, so with one identity the verdict is posted as a COMMENT with the verdict in the body; a bot account (stretch S4) removes that.

## 2026-10-07 — Under burst the LLM stage is the bottleneck, not the runners
56-PR burst with cap 4 / pool 4 / reasoning effort high: runners finish each task in ~4s, pool refill ~6s, so the runner stage drains at roughly one task per 2s. The review stage (gpt-6-astra at high effort, 40-70s per PR) ran on a 4-thread pool, so tasks piled up in `reviewing` (26 at the peak) and time-to-comment grew to 60-90s even though wait-for-runner was the visible number. The admission cap bounds CPU-bound test runs; the LLM stage is I/O-bound and wants its own, much larger concurrency. Change: `REVIEW_WORKERS` (default 12) separate from `ADMISSION_CAP`, plus a `prr_reviews_in_flight` gauge so the dashboard shows which stage is queuing. Good talk point: one "concurrency" knob is wrong when the pipeline has stages with different resource profiles.

## 2026-10-07 — GitHub secondary rate limit on review creation
21 of the first ~45 review posts failed with 403 (secondary rate limit: too many content-creating requests from one identity in a short window). Findings and verdicts were already in Postgres, so eval scoring was unaffected, but the PRs show no comment. Fix: a single posting lock with a 1.5s minimum gap between review creations and backoff honoring `Retry-After`. Circus's "128 agents" would hit this hard with one bot identity; a GitHub App gets per-installation limits.

## 2026-10-07 — Eval run 1 (56 PRs × 2 configs, gpt-6-astra @ effort=high, judge gpt-6-luna)
- **full** (diff + touched files + pytest/ruff): strict recall 35/36, semantic 35/36, FP 0/20, p50 time-to-comment 67s under a 56-PR burst (cap 4).
- **diff_only**: strict 34/36, semantic 33/36, FP 0/20.
- Historical bugs (IPv6 ×2, secret-key rotation, `--help`, provide_automatic_options): 8/8 both configs.
- Tokens: mean 4.0k in / 0.4k out per review; 0.45M in total for 112 reviews. LLM p50 16.6s, p95 36.7s at high effort.
Three lessons:
1. **Ceiling effect.** Single-line mutations in a 2-line diff are easy; the diff alone is nearly enough. The two configs differ by one or two PRs, which is inside the noise of n=36. Hence the `noisy` variant: same mutant hidden inside a real 50-200 line upstream change.
2. **One "miss" was the reviewer being right.** `elif len(matches) > 1` → `>= 1` after `if len(matches) == 1: return` is an equivalent mutant. The reviewer APPROVEd and explained exactly why. Marked `equivalent`, excluded from recall. Mutation-testing literature calls this the equivalent-mutant problem; it is why synthetic recall needs a human pass.
3. **Judge disagreement.** The judge rejected one correct finding (SESSION_COOKIE_SECURE default flip, "breaks HTTP sessions") as not matching the defect description. Report strict and semantic side by side rather than trusting either alone.
Also: 0 false positives on 20 real merged changes is suspicious in a good way; with a bigger clean set I'd expect some. Worth saying out loud rather than claiming perfection.

## 2026-10-07 — Noisy variant v1 was not noisy: merge-base diffs
Plan: hide a mutant inside a real upstream change by opening the PR against `clean-base/<sha>` (= main minus commit C) with head = main + mutation. Result: every "noisy" PR touched exactly one file. Both the runner and GitHub compute PR diffs from the **merge-base** of base and head, and clean-base branched *off* main, so the merge-base was main and C vanished from the diff. Fix: build head as a descendant of clean-base (cherry-pick C back on, then mutate). Lesson for the slide: a PR's base branch is not "what the diff is against"; the merge-base is.
Also two of the 13 "misses" were equivalent mutants (deleting a docstring; deleting `rv = t.cast(Response, rv)`, a runtime no-op). The mutator now skips both. On the 11 real noisy bugs the reviewer went 11/11. Twice now the eval was wrong before the reviewer was.

## 2026-10-07 — Noisy v2 (bug inside a real upstream diff, 2-6 files)
11 PRs. full: 10/11 strict and semantic. diff_only: 11/11 strict, 10/11 semantic. p50 time-to-comment ~45s quiet. The one miss (removed early-return guard in `Flask._check_setup_finished`-area code) was caught by diff_only and missed by full, so at n=11 the two configs are indistinguishable; the honest statement is "context beyond the diff did not measurably help on this corpus," not "full is better". What *would* separate them: bugs whose evidence lives outside the diff (callers, fixtures), and red-test bugs where pytest output names the failure. Red variants were 10/10 in both configs, so even there the diff sufficed for single-hunk reverts.
Net after three eval passes: reviewer 56/58 on non-equivalent bugs across all variants and configs; 0/20 false positives; eval harness was wrong (equivalent mutants, merge-base noise) more often than the reviewer was.

## 2026-10-08 — S5: where the money goes
Cost model: compute = runner seconds × node $/hr × (runner CPU limit / node vCPU); tokens at list price (gpt-6-astra $10/$50 per 1M in/out, from the OpenAI pricing page). A typical review: 4k input tokens ≈ **$0.04–0.06**; a big one (19k tokens) **$0.21**. Compute for the same PR: **$0.00004**. Four warm runners standing idle: **$0.16/hour** ≈ $118/month ≈ the token bill for ~2,000 average reviews. Below ~70 PRs/day the idle pool costs about as much as the tokens; above that, tokens dominate completely. The runner is not where the money is. Judge (gpt-6-luna) is 100× cheaper per token than the reviewer.

## 2026-10-08 — S9: Secrets Manager via Pod Identity
Controller now boots with `SECRETS_ID=pr-runtime/app`, fetches the JSON secret through its Pod Identity role (`secretsmanager:GetSecretValue` on that one ARN) and exports keys into its environment before settings load. No k8s Secret is mounted into the controller any more (`envFrom` gone); Postgres still takes its password from the k8s Secret. Caveat worth saying out loud: the values are seeded by Terraform from `.env`, so they sit in local Terraform state; a team setup would seed them out-of-band and keep state in encrypted S3.

## 2026-10-08 — S3: Karpenter for burst capacity
Fixed node group (3× m7g.large) stays as the floor; Karpenter `NodePool` adds Graviton nodes (m7g/c7g/r7g/m8g/c8g, large–2xlarge, spot preferred, on-demand fallback) when runner pods are unschedulable and consolidates them away after 60s idle. IAM via the EKS module's karpenter submodule with Pod Identity; interruption queue + EventBridge rules for spot termination / rebalance / health events.
Measured: scale warm pool 4 → 16 at t=0; NodeClaim at t+4s; node Ready at t+41s; all 16 runners Running at t+49s (9 of them on the new c7g.2xlarge). Karpenter chose **on-demand**, not spot. Log: `AuthFailure.ServiceLinkedRoleCreationNotPermitted: The provided credentials do not have permission to create the service-linked role for EC2 Spot Instances.` This account had never launched a Spot instance, so `AWSServiceRoleForEC2Spot` did not exist and Karpenter's role may not create it. One-time `aws iam create-service-linked-role --aws-service-name spot.amazonaws.com` fixes it. Second account-shaped surprise after the vCPU quota: capacity is an account-state problem before it is a scheduler problem.
Also fixed the slow path: a busy runner whose pod vanishes (node consolidation, spot reclaim, eviction) used to be noticed only at the 300s deadline. The scheduler now diffs busy pods against live pods every tick and requeues immediately (`prr_tasks_lost_total{reason=pod_lost}`); attempts cap raised to 3 since node loss is not the task's fault.

## 2026-10-08 — S1: mined guidelines, "compiled not written"
743 upstream `pallets/flask` review comments (2016→2026) mined via the API, distilled by gpt-6-astra into 44 rules across `src/flask/`, `tests/`, `docs/`, each linking the PRs it came from (e.g. FLASK-01 "preserve the None-vs-falsey distinction when changing conditions", FLASK-08 "do not swallow unexpected exceptions or classify factory failures by message text"). Loaded per touched directory in a `guided` config.
Result on the 46-bug / 20-clean corpus: **45/46 strict and semantic, FP 0/20, identical to `full`**, at +3.6k input tokens (~+$0.04) per PR. No lift and no noise. Honest reading: this corpus measures defect detection; guidelines encode *conventions* (scoping, docstrings, typing policy, sans-IO boundaries), which the corpus never violates. To show their value you need a convention-violation corpus, which is what the console's thumbs-down feedback would build over time. Toy version of Rover's "3,744 standards, each traceable to its origin" is real; the measurement that would justify it is not, yet.

## 2026-10-08 — Cross-file bug variant: negative result
Tried to build the one corpus where an agentic reviewer should beat context-stuffing: flip a boolean/int default in a function signature in file A when callers in other files rely on the default. 22 candidate sites in `src/flask`, 6 with cross-file callers, **0 survived the test suite**. Flask's tests cover every cross-file default they rely on. So on this codebase there is no cheap way to manufacture "evidence lives outside the diff" bugs; the historical fixes are the only realistic source and all of them were caught from the diff alone. Kept the generator (`eval/mutate_xfile.py`) for a larger repo. Agentic config still gets measured on the existing corpus for latency and cost.

## 2026-10-08 — The drain test evicted the controller
Drain test v2 drained the Karpenter spot node mid-task and the controller API vanished: after the previous rollout restart, the scheduler had placed the *controller* pod on the burst node (it had the most free CPU). Draining it killed the control plane, not just runners, and Karpenter then consolidated the node away. Fix: `nodeSelector: pr-runtime/pool=general` on the controller and Postgres so only runners float onto burst capacity; a PodDisruptionBudget would be the next layer. Lesson for the talk: once you add elastic nodes, "what is allowed to live on them" is a design decision; the default is "everything", which is wrong for stateful and control-plane pods. The lost-pod requeue path still needs a clean demonstration (v3).

## 2026-10-08 — S2 result: the agentic loop costs 2× and finds nothing extra here
`agentic` config (read_file / grep / list_dir against a bare git mirror in the trusted controller, 15-call budget, same base prompt as `full`): **45/46 strict, 43/46 semantic, FP 0/20**. Mean input tokens 24.3k vs 11.5k for `full`; $0.26 vs ~$0.11 per PR at list price; p50 time-to-comment 145s vs 58s (serial tool round-trips at high reasoning effort). Same strict recall, slightly worse semantic (two findings the judge rated as nearby-but-not-the-defect after the model wandered). On a corpus where every bug is visible in the diff, exploration is pure cost. The honest four-way summary: diff_only ≈ full ≈ guided ≈ agentic on recall; they differ only in cost and latency, and diff_only is the cheapest by far. What *would* change the ranking is a corpus with cross-file evidence, which this codebase's test suite would not let me build (see above).

## 2026-10-08 — Drain test v3: lost-pod requeue works
Spot c7g.2xlarge burst node with 9 runners; 8 reruns fired (cap 4 → 4 busy, 2 pending, 2 already reviewing); node drained 1s later. One busy task's pod was on the drained node: the scheduler logged "runner pod disappeared (node loss or eviction)", requeued it immediately (`prr_tasks_lost_total{reason="pod_lost"} 1`), and it posted on attempt 2 with total 50s. All 8 posted, 0 failed, nothing waited for the 300s deadline. Control plane and Postgres stayed on the fixed nodes this time. This is the answer to "what happens on a spot interruption mid-test".

## 2026-10-08 — The laptop kernel-panicked; builds and evals move to a driver box
At 04:19 the laptop ran out of memory (kernel jetsam killing processes every second), froze, and the hardware watchdog panicked it at 04:21 (`watchdog timeout: no checkins from watchdogd in 93 seconds`). Running at the time: a Docker Desktop `docker build` of the controller image (node + vite + python layers), Karpenter install, two `kubectl port-forward`s, the drain-test script, eval tooling, Chrome. Nothing was lost (everything was committed; the cluster does not depend on the laptop), but it should never have been the laptop's job.
Fix: `infra/driver.tf` adds an arm64 **t4g.large driver instance** in a private subnet, no SSH key, reachable only via SSM (`scripts/driver.sh '<cmd>'`), with Docker, kubectl, Helm, uv, gh, the repo, and cluster-admin through an EKS access entry on its instance role. Secrets come from Secrets Manager via `scripts/driver_env.sh`; nothing is typed on a laptop. ~$1.60/day. The laptop keeps only `kubectl` and a port-forward for the demo. Same lesson as the storage-bench sweeps: the thing that must stay up should not be the thing you close the lid on.

## 2026-10-10 — A routine `terraform apply` rolled every node
Applying an unrelated change (Lambda code, a new secret key) also updated the managed node group's AMI release (`1.34.11-20260930` → `20261003`): the EKS module tracks the latest release unless told otherwise, so any apply after AWS publishes a new AMI becomes a rolling node replacement. Pods moved (controller, Postgres within its AZ), the apply errored mid-way with `Nodegroup cannot be updated as it is currently not in Active State`, and the Lambda change still landed. Fix: pin `ami_release_version` (`var.node_ami_release`) and bump it on purpose. Lesson for the talk: "latest" defaults in IaC are a scheduled surprise; pin anything whose change means a rollout.

## 2026-10-10 — S4: GitHub App instead of a PAT
The reviewer now authenticates as a GitHub App: the controller signs a JWT with the App's private key (Secrets Manager), exchanges it for an installation token (1h, scoped to that installation's repos and the declared permissions: pull requests write, checks write, contents read, issues write), and caches it per installation. Reviews post as `pr-runtime[bot]`, so real APPROVE/REQUEST_CHANGES verdicts instead of the self-review COMMENT fallback. Two triggers: every PR event (auto), or an `@pr-runtime` mention in a PR comment (the Lambda filters `issue_comment` events for the handle; the controller reacts with 👀 and reviews the PR head). A `.pr-runtime.yml` with `mode: mention` turns auto off per repo. Each task also opens a **Check run** that completes as `failure` when a blocker/major finding exists, `neutral` for minors, `success` when clean. The bot can block a merge through a required check; it never approves one. That is the separation to defend: bot = evidence, humans or rulesets = decision. Rate limits are now per installation, which removes the burst-posting problem from Oct 7.

## 2026-10-10 — S8: any repo, not just the Flask fork
The runner no longer assumes Flask. For a task on repo X it reuses the baked seed only if X is the seed repo (marker file; dependency install skipped); otherwise it partial-clones (`--filter=blob:none --no-checkout`), fetches the two shas, and detects the toolchain: `uv.lock`/`pyproject` → `uv sync` + `uv run pytest`; `requirements.txt` → venv + pip; `package.json` → npm; `go.mod` → go test; nothing → diff-only review with a note. A repo can override with `.pr-runtime.yml` (`install`, `test`, `lint`, `timeout`, `mode`). The prompt names the repo and language instead of "Flask". `REPOS` allowlist defaults to empty = any repo the App is installed on. Measured on `pallets/click` (never seen before, main vs 8.3.0, 119 files): clone 0.4s, install 3.0s, 2,238 tests in 14.7s, 18.7s total; the warm Flask path stays ~4s. So "what the warm clone buys" is about 15s per task on a mid-size Python repo, almost all of it the test suite, not the clone. Not done: private repos (the runner would need a scoped read token, breaking "zero secrets in the pod"), node/go toolchains in the image (detected, but the binaries aren't installed), and per-repo fairness caps.

## 2026-10-10 — Check run ids don't fit in INTEGER, and a crash between insert and enqueue
First Check run on the click fork: created fine (`in_progress`, "Reviewing"), then storing its id failed with `NumericValueOutOfRange: integer out of range`. GitHub check-run ids are ~1.1e11; the column was 32-bit. The exception fired *after* the task row was committed and *before* `enqueue()`, so the task sat `queued` in Postgres with no in-memory entry and nothing would ever run it. Three fixes: `BIGINT` for `check_run_id` and `installation_id` (with an idempotent `ALTER COLUMN` migration), check bookkeeping wrapped so a Checks API problem can never block the review, and `reconcile()` now re-enqueues every DB-`queued` task on boot, which is how the stuck one was recovered: the next rollout logged "1 queued re-enqueued" and it posted a second later. Verified after: a fresh mention produced a completed check, conclusion `failure`, title "1 blocking finding(s)".

## 2026-10-10 — Closing the autoscaling loop: the pool scales, time-to-comment does not improve
**Wired.** `ADMISSION_CAP=0` (new default) makes the cap follow the pool: each scheduler tick the effective cap is the number of Ready runner pods (`prr_admission_cap`, `prr_runners_ready`; `/api/stats` reports `cap_mode: pool` and prices the standing pool from the live count). A positive value is still a fixed override. A KEDA `ScaledObject` (`deploy/chart/templates/keda-scaledobject.yaml`, `runner.autoscale.*`) reads `max(prr_tasks_pending)` from Prometheus every 5s and drives an HPA on the runner Deployment: one pending task per runner, 4..16 replicas, scale-up unbounded, scale-down 120s window then 4 pods/min. Karpenter adds a spot node when the new pods go Pending. The HPA only sets `.spec.replicas`; the ReplicaSet keeps that many pods alive, so the controller's delete-after-one-task behaviour is unchanged. `REVIEW_WORKERS` default 32.

**Measured.** Same 56 PRs as the Oct 7 burst (`bug/*` and `clean/*` on the fork), re-fired through `POST /api/tasks/{id}/rerun` in 3.4s by `scripts/burst_rerun.py` from the driver box; per-task timings from Postgres for both runs.

|---|---|---|
| arrivals | 56 PRs opened by `gh` over 37s (webhooks) | 56 reruns in 3.4s |
| time-to-comment p50 / p95 | 70.1s / 200.3s | 164.8s / 242.2s |
| wait for runner p50 / p95 | 38.9s / 73.2s | 39.8s / 61.9s |
| runner p50 | 4.0s | 4.1s |
| LLM p50 / p95 | 16.0s / 28.7s | 9.3s / 18.0s |
| GitHub post p50 / p95 | 1.6s / 1.8s | 100.2s / 131.4s |
| runner stage drained (pending=0, busy=0) | ~105s | 86s |
| last review posted | t+258s | t+253s |
| pool max / burst node | 4 / none | 16 (desired at t+10s, 16 Ready at t+78s) / 1× c8g.2xlarge spot, claimed t+10s, Ready t+42s, gone t+~360s |
| failed / retried | 0 / 0 | 0 / 0 |
| tokens | 436k in / 20k out ≈ $5.39 | 489k in / 23k out = $6.04 |
| compute | ~$0.003 runner-seconds | $0.003 runner-seconds + ~$0.016 burst node (6 min of $0.15–0.18/hr spot) |

**What scaled when.** Pending jumped to 52 at t+9s; KEDA/HPA asked for 16 at t+10s (5s scrape + 5s poll); Karpenter had a NodeClaim at the same tick and the node Ready at t+42s; 16 runners Running at t+78s; pending hit 0 at t+81s. Pending stayed 0, so after the 120s stabilization the HPA stepped 16→12→8→4 at t+175/235/295s and Karpenter consolidated the empty node ~60s after its last pod. Zero lost pods, zero requeues: scale-down never picked a busy runner.

**Honest reading.** The loop works mechanically and the runner stage is no longer the bottleneck, but time-to-comment got *worse*, and for two reasons that have nothing to do with pods:
1. **Serialized GitHub posting is now the dominant term.** Every write (review + check-run finish, two per task) goes through one lock with a 1.5s gap, so a task costs ~3.5–4s of posting and 56 tasks have a ~170s floor of pure gaps; with 32 review workers finishing together, 40+ reviews queued on that lock (`post` p50 100s). The fixed pool hid this: 12 workers and a 37s-spread arrival metered reviews out at roughly the rate the lock could post them, so `post` looked like 1.6s. The review worker also holds its slot (and its DB session) while waiting for the lock, so `prr_reviews_in_flight` reads 40+ when the LLM is mostly idle. Fix candidates, not done: post the review and finish the check in one write, drop the gap toward GitHub's documented 80 content writes/min (0.75s), or move posting to its own queue so the LLM pool is not blocked.
2. **The ramp costs about what it saves.** Node Ready at 42s plus image pull and seed copy on a fresh node means 16 Ready pods at ~78s; at the floor the runner stage would have drained in ~105s anyway. For a 56-PR burst of 4-second tasks the elastic pool buys ~20s of runner-stage time. It would matter for a repo whose tests take minutes (click: 15s; a real suite: 5–20 min), which is the case to show rather than Flask.
Also: with the cap tied to Ready pods, the cap *dips* while the pool refills (cap=1–2 at t+15–45s in both runs) because each pod serves one task and its replacement takes 10–20s to become Ready; the pod-per-task boundary is a throughput tax that autoscaling does not remove. The two runs are not perfectly matched (arrival spread, 12 vs 32 workers, the LLM was faster today), so the honest claim is: autoscaling moved the queue, it did not shorten it.

**What broke on the way.** The first autoscaled run stalled: `REVIEW_WORKERS=32` against SQLAlchemy's default pool (5 + 10 overflow). Each review worker holds a session for its whole LLM call, so workers blocked on connections, `/api` timed out (the measurement script died), and three `on_result` writes timed out *after* the runner pod had been released, leaving tasks `running` in Postgres with no in-memory owner until the next restart's `reconcile()` requeued them (it did; all 56 eventually posted, 3 on attempt 2). Fixes: pool sized to `review_workers + 12` (+16 overflow), and a 30s `sweep_orphans()` that requeues DB-`running` tasks the scheduler is not tracking. Lesson: raising one concurrency knob silently assumes every pool behind it is at least as wide.


## 2026-10-10 — The runner can't clone it? Review the diff anyway (API-diff fallback)
**Why.** The trust split says the runner pod holds no credentials, so it clones anonymously. That is fine for public forks and useless for a private repo: `git clone` fails on "could not read Username", the task went `failed`, the Check closed `neutral` "Runner failed", and the PR got nothing. Same outcome for a bad ref or a runner crash. A reviewer that goes silent exactly when the repo is private is the wrong failure mode; the diff-only arm of the eval scored the same recall as `full` on this corpus, so a diff-only review is worth posting.

**How.** `scheduler.on_result` no longer fails the task on a runner error. It calls `scheduler._fallback_review`, which fetches through the controller's installation token (`github.pr_context`): the PR diff (`GET /pulls/{n}` with `Accept: application/vnd.github.diff`), the changed-file list (`/pulls/{n}/files`, paginated), and the head contents of each touched file (contents API, raw, same caps as the runner: 200k chars, skip NUL-bearing and oversized files, skip removed ones). Those land on the task as if a runner had produced them with no test run (`pytest_rc`/`ruff_rc` None, `meta.fallback = {reason, source: "github_api"}`, no `meta.toolchain`), state `reviewing`, and the normal review runs under `diff_only` semantics whatever config was requested (`reviewer.effective_config`; `task.config` keeps the requested value so dedupe and eval rows are untouched, and scoring can exclude `meta.fallback` rows). The prompt, the review body and the Check all carry one line: "Tests not run: <reason>. Review is from the diff only."; the Check title gets "(tests not run)" and the conclusion follows the findings as usual. Only when the API fetch itself fails does the task go `failed` with a neutral Check, as before. `prr_fallback_reviews_total` counts them.

**The test.** The App is installed on `anthonyzhao27/{flask,click}` only, both public, so a private PR could not be driven end to end without changing the installation (a branch on `intern-radar` was opened and closed; no event arrived). Instead `CLONE_URL_OVERRIDE` (a controller env knob, never in the chart) pointed every assignment at `https://github.com/does-not-exist/x.git` and the click PR #1 task was rerun: the runner reported `git clone failed: fatal: could not read Username for 'https://github.com'`, the controller fetched 1 file via the API in 0.7s, and `pr-runtime[bot]` posted review `#pullrequestreview-5481070668` in 24.5s total with the "Tests not run" line, `config diff_only`, `meta.fallback` set, state `posted`, Check `success` titled "No findings (tests not run)". Honest footnote: with tests the same PR had been caught every time (`termui.py:294`, flipped `show_default` default); from the diff alone the model called it a behaviour change and approved. The override was removed by `kubectl set env ... CLONE_URL_OVERRIDE-` after the test.

**Not done.** Running a private repo's tests would need a scoped read token in the pod, which breaks the "zero secrets in the runner" line; the fallback keeps that line and labels what it costs.

## 2026-10-10 — Posting: per installation, one gap per task, and what the third burst actually showed
**What changed.** `github.py` had one global lock and one 1.5s gap for every write. Now each identity (installation id, or `"pat"`) has its own lock + last-write timestamp (dict behind a small global lock), the gap is per *slot* rather than per request (`post_slot()`: a task's review POST and check-run PATCH go back to back, one gap to the next task; ~52 writes/min worst case, under GitHub's 80/min content-write ceiling), and the Retry-After / secondary-limit backoff is unchanged and logged. Check-run opens moved off the ingest path to a one-thread executor, because an inline serialized write would meter task creation at ~40/min. Reruns of PAT-era tasks inherit the repo's installation, so the burst posts as the App with a Check per task.

**The honest limitation, stated up front.** Every test PR lives under one installation (`anthonyzhao27`), so per-installation buckets cannot help a single-tenant burst at all; they only stop one tenant's burst from queueing another's. The only lever inside the constraints (keep the 1.5s gap) was fewer gaps per task.

**Two things broke on the way.**
1. **Deadlock across a Python lock and a Postgres lock.** The first run of this burst posted nothing: 32 review threads sat idle-in-transaction and the check opener was stuck on `UPDATE tasks SET check_run_id`. The opener held the posting slot while updating the task row; the review thread held that row (assigning `findings` autoflushes the verdict UPDATE) while waiting for the slot. Neither the Python lock nor Postgres's deadlock detector can see the other half. Fix: no DB work while holding a slot in the opener, and the review result is committed before the slot is taken. The 56 wedged tasks were failed in Postgres and the burst rerun. Lesson for the talk: a lock you hold across any other blocking resource is a deadlock with extra steps; keep the critical section to the one thing it serializes.
2. **The Oct 10 diagnosis was wrong about which two writes.** The autoscaled burst had no Check runs (PAT-era tasks, `installation_id` null) so it was not "review + check finish". It was the PAT **self-review 422 + retry**: every review by the PR's own author is refused with `APPROVE/REQUEST_CHANGES`, downgraded to `COMMENT` and re-posted, so each task cost two gaps, ~4.2s, and 56 tasks ≈ 235s of posting, which is exactly where "last posted t+253s" came from. Posting as the App has no self-review, so the review is one write. That, not the bucketing, is most of the gain below.

**Measured** (`eval/results/burst-20261010-posting/summary.md`, same 56 PRs, reruns fired in 3.8s):

Review posts ran at one per ~2.5s (gap + POST) from t+12s to t+151s; the LLM stage finished at t+87s, so the last minute is pure posting backlog with 31 workers queued on the slot. Against the fixed Oct 7 run the p50 is still 11s worse (the autoscaled ramp, see the previous entry) and the p95 is 57s better (32 workers, no 422 retry). No 403/429 at any point; 167 writes in 327s, gap p50 1.99s.

**What the one-gap-per-task change actually gave.** Less than designed: the lock is not fair, so under the burst the 32 review threads out-competed the single check-opener thread; only 9 of 56 tasks had their Check open when the review posted (and paid one gap for both writes). The other 47 had the Check opened *after* the review, then finished in a second slot, which is why writes trail to t+330s while reviews ended at t+151s. Reviews first, Checks later is the right priority for time-to-comment, but two writes for a late Check is waste; the follow-up commit creates a late Check already completed (one POST). Not re-measured at 56; a 6-PR mini burst exercised the path. Remaining candidates if posting is ever the bottleneck again: the gap itself (GitHub's limit is 80/min, i.e. 0.75s), or one write per task by folding the review into the Check output.
